# 架构

## 目标

单机器人、单部署。没有桌面界面，所有能力通过本地 HTTP API 暴露；插件运行在
独立进程中，崩溃不影响机器人本体。

## 进程划分

| 进程 | 语言 | 职责 |
| --- | --- | --- |
| `botd` | C++ | 连接、登录、协议编解码、世界状态、反作弊握手、底层动作 |
| `hub` | Go | 生命周期管理、对外 API、WebUI、插件宿主、日志与指标 |
| 插件 | 任意 | 业务逻辑，通过 API 订阅事件、查询状态、下发动作 |

只有 `hub` 对用户暴露端口；`botd` 只监听回环地址上的内部接口。

## 端口

| 端口 | 服务 | 开启条件 |
| --- | --- | --- |
| 3030 | API | 总是 |
| 3031 | WebUI（静态资源） | 总是 |
| 3032 | 调试服务，SSE 实时日志 | `debug: true` |
| 3039 | botd 内部接口，TCP + 行分隔 JSON | 总是 |

## 热路径规则

**收包 → 解析 → 更新世界状态 → 发包 必须留在 botd 进程内。** 区块包频率很高，
把它序列化穿过进程边界再回来会同时放大延迟和 CPU。跨进程只传三类数据：

- 命令：bot 要做什么
- 事件：世界发生了什么（带单调递增 seq）
- 快照：当前状态，用于新订阅者或断线重连后的重新同步

世界查询采用拉取而不是推送：插件要哪块查哪块，不要订阅全量区块。

## 事件模型

- 每个事件带 `seq`，全局单调递增，重连后可以带 `since_seq` 回放。
- 订阅带 topic 过滤，由 botd/hub 侧筛选，不把原始包全量推给插件。
- 每个订阅一个有界队列。队列满时丢弃最旧事件并记录丢失区间，慢插件不能阻塞核心。
- 新订阅者先拿快照，再消费 `seq` 更大的事件，避免“连上来之前发生的事丢了”。

## 重连语义

- `botd` 与服务器重连成功后必须发 `session.reset`：旧实体 runtime id、旧区块缓存
  全部作废。插件收到后只能基于新快照工作。
- 插件崩溃后由 hub 重启，重启后的第一个动作是拉快照，不能假设内存状态还在。
- 命令带 `request_id`，重复投递不得产生重复执行。

## 插件

- 插件以独立进程运行，通过标准输入输出的 JSON-RPC 与 hub 通信；Go 插件也可以
  直接调用 hub 的 HTTP API。
- 权限在清单中声明：读聊天、发聊天、执行命令、读世界、写世界、原始包。
- 原始包能力默认关闭，属于显式授权的调试能力。
- 反作弊应答属于核心职责，不下放给插件；插件卡住或抛异常不能导致机器人被踢。

## 阶段划分

1. hub 骨架：三个端口、健康检查、SSE 日志（完成）
2. 插件宿主：清单、权限、JSON-RPC、崩溃重启（完成）
3. botd 底座：帧与包编解码、会话、事件序列、本地控制接口（完成）
4. 真实连接：RakNet、登录链、反作弊握手（进行中）
5. 世界状态：区块、方块表、实体，查询 API（待接入）
6. 动作：移动、批量放置、命令（模拟层已完成，待接真实协议）
7. 协议对拍工具与版本升级流程（待开始）
